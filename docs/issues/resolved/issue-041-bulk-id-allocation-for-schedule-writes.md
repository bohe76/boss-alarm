# Issue-041: 스케줄을 행마다 ID 할당·저장해 수천 건 적재가 느림

## 1. 개요 (Overview)

`DB.nextId()`는 호출할 때마다 `v3_uid_counter`를 localStorage에서 읽고 다시 쓴다. `DB.replaceSchedulesByGameId`는 ID가 없는 행마다, `DB.addSchedulesBulk`는 모든 행마다 `nextId()`를 부르므로 행 수만큼 localStorage 쓰기가 일어난다. 수천 건을 직접 실은 조작 공유 링크를 열면 부팅이 분 단위로 느려진다.

issue-040 코드 리뷰 대응 중 측정했고, 사용자 결정으로 v3.0.6 범위에서 빼 별도 이슈로 남긴다.

## 2. 문제점 또는 요구사항 (Problem or Requirement)

- **측정** (Chromium, 스케줄 5,000건 × 200자 메모, URL 약 155만 자): 부팅 약 2분. 프로파일상 `loadInitialData` → `DB.replaceSchedulesByGameId` → `nextId` → `save`가 42초(5,000회, 건당 약 8ms).
- **건당 8ms인 이유 (측정에서 추정)**: 주소창에 긴 공유 URL(`#d=…`)이 남아 있는 동안에는 localStorage 쓰기 한 번이 느려지는 것으로 보인다. 해시는 적재가 성공한 뒤에 지운다(실패 시 외부 브라우저에서 다시 시도할 수 있게 남겨 두는 설계). 주소가 짧을 때는 같은 쓰기가 훨씬 빠르다 — 5행짜리 링크가 10,000행으로 확장되는 경우(쓰기 약 1만 회)는 부팅 약 1초였다.
- **영향 범위**: 예외는 나지 않고 상태도 일관된다. 프리셋 링크와 커스텀 목록 링크 모두 같은 경로이며 v3.0.5 배포본에도 있다. 정상적인 공유 링크(수백 건 이하)에서는 체감되지 않는다. 브라우저의 URL 길이 제한(Chromium 약 2MB) 때문에 실을 수 있는 양은 200자 메모 기준 6,000건 안팎으로 추정한다.
- **부수 효과**: 48시간 확장(`_expandAndReconstruct`)은 확장 결과에 ID를 넣지 않고 `replaceSchedulesByGameId`에 넘기므로, 확장할 때마다 전체 행의 ID를 새로 받는다. 정상 사용(수백 행, 짧은 주소)에서는 문제가 되지 않지만 같은 원인이다.

## 3. 제안된 해결 방안 (Proposed Solution)

`src/db.js`는 보호 영역이다(`DB` 싱글톤 전체, `nextId()` 포함). 아래는 제안이며 사용자 승인 뒤 진행한다.

1. **ID 일괄 할당**: `replaceSchedulesByGameId`와 `addSchedulesBulk`에서 카운터를 한 번 읽고, 필요한 만큼 순서대로 배정한 뒤, 한 번만 저장한다. 행 수와 무관하게 카운터 쓰기가 1회가 된다. `nextId()`의 공개 동작(1씩 증가하는 정수, `v3_uid_counter`)은 그대로 둔다.
2. **대안 — 해시를 적재 전에 지우기**: `loadInitialData`에서 DB 쓰기 전에 `history.replaceState`로 해시를 지우고 실패하면 되돌린다. 쓰기 횟수는 그대로이고 "실패 시 해시 보존" 설계를 건드리므로 1번보다 못하다.
3. **검증 계획**: `test/db.test.js`에 일괄 할당 뒤 ID가 유일하고 카운터가 마지막 ID와 같다는 테스트, 저장 실패(용량 초과) 시 카운터와 스케줄의 정합성 테스트를 추가한다. 5,000건 링크의 부팅 시간을 수정 전후로 잰다.

**예상 영향 범위**: 스케줄을 여러 건 쓰는 경로(공유 링크 적재, `commitDraft`, 48시간 확장)가 `replaceSchedulesByGameId`를 지난다. ID 값의 순서가 같아야 하고, 중간에 저장이 실패했을 때 카운터가 앞서 나가거나 뒤처지지 않는지 확인이 필요하다.

## 4. 해결 과정 및 최종 결과

- **브랜치**: `main` (로컬 작업, 2026-11-20, 커밋 `f96dced`). 보호 영역(`src/db.js`) 수정은 사용자 승인("1번으로 해도 문제 없는지 검토하고, 문제없으면 진행") 후 진행했다.
- **채택한 안**: 3장의 1번(ID 일괄 할당). 2번(해시를 적재 전에 지우기)은 쓰지 않았다.
- **구현** (`src/db.js`)
  - 모듈 내부 함수 `createIdBatch()`를 추가했다. 카운터를 한 번 읽고, `next()`로 ID를 순서대로 내주고, `commit()`에서 한 번만 저장한다.
  - `replaceSchedulesByGameId`와 `addSchedulesBulk`가 `this.nextId()` 대신 이것을 쓴다. `id`가 비어 있는 행에만 새 ID를 주는 조건(`s.id ||`)과 배열 순서는 그대로다.
  - 카운터는 스케줄보다 먼저 저장한다(수정 전과 같은 순서). 할당한 ID가 없으면 카운터를 쓰지 않는다.
  - `nextId()`, `addSchedule`, 보스 경로, `importAll`/`exportAll`은 건드리지 않았다. `DB`에 공개 메서드를 더하지 않았다.
- **수정 전과 같은 점**: 내주는 ID 값·순서와 마지막에 남는 `v3_uid_counter` 값이 `nextId()`를 그만큼 부른 결과와 같다. 손상된 카운터 값(`"abc"`, `{}`, `[1,2]`, `1e400` 등 — 앱은 만들지 않고 개발자도구로 직접 고쳐야 생긴다)에서도 같다. `nextId()`는 매번 저장하고 다시 읽으므로 유한하지 않은 값이 `null`로 저장돼 다음 호출이 0부터 다시 세는데, `createIdBatch()`가 이 동작을 그대로 따른다.
- **수정 전과 다른 점 (받아들임)**
  - 카운터 저장만 실패하는 경우(용량 초과): 수정 전에는 그 묶음의 행이 모두 같은 ID를 받았다. 수정 후에는 묶음 안의 ID가 서로 다르다. 저장된 카운터가 뒤처지는 것은 양쪽이 같다. 숫자 몇 글자가 늘 때 용량이 정확히 한계에 걸려야 하므로 드물다.
  - 할당할 ID가 없어도 카운터를 한 번 읽는다. 카운터가 손상돼 있으면 파싱 실패 로그가 1건 남는다. 저장 값은 바뀌지 않는다.
  - 같은 origin의 다른 탭으로 가는 `storage` 이벤트가 행 수만큼에서 1회로 준다. `src`에 `storage` 리스너가 없어 영향이 없다.
- **측정** (Chromium, 스케줄 5,000건 × 200자 메모, URL 약 161만 자, 주기 0 보스 3종, 같은 PC에서 `src/db.js`만 바꿔 비교)

  | | 부팅 | 카운터 쓰기 | 카운터 쓰기에 든 시간 | 적재 행 / 최대 ID / 카운터 |
  |---|---|---|---|---|
  | 수정 전 | 134.8초 | 10,141회 | 43.9초 | 5,000 / 10141 / 10141 |
  | 수정 후 | 8.9초, 12.2초 (2회) | 143회 | 1.3~1.8초 | 5,000 / 10141 / 10141 |

  수정 후에 남은 카운터 쓰기 143회는 프리셋 보스 등록(`upsertBoss` → `nextId()`) 141회와 일괄 쓰기 2회(링크 적재, 48시간 확장)다. 부팅 시간은 쓰기에 든 시간보다 훨씬 크게 줄었다 — 쓰기 1만 회가 브라우저 쪽에 쌓여 처리되는 시간까지 사라진 것으로 추정한다(측정하지 않음).
- **남은 한계 (고치지 않음)**: 48시간 확장은 여전히 확장할 때마다 전체 행의 ID를 새로 받는다(2장의 부수 효과). 이제 쓰기가 1회라 느리지는 않다. ID가 바뀌는 것 자체는 이 이슈의 범위가 아니다.
- **독립 리뷰**: 승인. 1차에서 손상된 카운터 값(`"abc"`, `1e400`)일 때 ID 열과 저장 값이 수정 전과 다르다는 지적을 받아 `createIdBatch()`를 위와 같이 보완했다. 2차에서 수정 전 코드와 카운터 값 36종 × 행 묶음 7종 × 메서드 2종(504건)을 비교해 차이 0건을 확인했다.
- **검증**
  - `test/db.test.js` `Bulk ID allocation (issue-041)`: ID 값·순서(지정 `id` 유지, 빈 `id`는 새로 할당), 카운터 쓰기 1회, 할당이 없으면 쓰기 0회, 카운터 → 스케줄 저장 순서, 스케줄 저장 실패 시 카운터가 내준 ID보다 뒤처지지 않음, 카운터 값 17종 × 1·3행을 `nextId()` 결과와 대조. ID 값·순서 테스트는 수정 전 코드에서도 통과하고, 쓰기 횟수 테스트는 수정 전 코드에서 실패(50회)한다.
  - `npm run lint` 통과, `npm test` 283건 통과, `npm run e2e` 13건 통과(1건은 실연동이라 건너뜀).
